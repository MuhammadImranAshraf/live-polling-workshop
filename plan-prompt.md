To ensure strict consistency across all machines, follow every specification below for folder structure, API contracts, database schemas, user flow, device capture, and Tailwind CSS visual design.

## 2. Backend Specification (`./backend`)

### Dependencies

- Runtime: `express`, `mongoose`, `cors`, `dotenv`, `bcryptjs`, `jsonwebtoken`
- Dev: `typescript`, `tsx`, `mongodb-memory-server`, `@types/express`, `@types/cors`, `@types/bcryptjs`, `@types/jsonwebtoken`, `@types/node`

### Database Connection & Zero-Config Fallback (`src/index.ts`)

- Try connecting to `process.env.MONGODB_URI` with a `2500ms` timeout. The default database URL (used in `.env.example`, and as the hard-coded fallback in `src/config.ts` when `MONGODB_URI` is unset) is `mongodb+srv://polling_db_user:polling_db_password@polling.omanrjh.mongodb.net/polling_db`.
- Call `app.set("trust proxy", "loopback")` so that, when the API is reached through a local tunnel or proxy (e.g. ngrok), `req.ip` resolves to the real client IP from `X-Forwarded-For` (and is never spoofable by direct, non-local callers).

### Mongoose Models

1. **User Model (`src/models/User.ts`):**
   - `fullName`: `String` (required, trimmed)
   - `email`: `String` (required, unique, lowercase, trimmed)
   - `studentId`: `String` (required, unique, trimmed, uppercase)
   - `passwordHash`: `String` (required)
   - `role`: `"student" | "admin"` (default: `"student"`)
   - `signupDevice`: optional embedded sub-document (no `_id`, `default: undefined`) describing the device the account was created from. Absent for seeded users and any account created before this feature. Fields (all `String` with default `""` unless noted):
     - `deviceName` (a human-readable name generated by the server, see "Signup Device Capture")
     - `deviceType`: `"mobile" | "tablet" | "desktop"` (default `"desktop"`)
     - `os` (e.g. `iOS`, `iPadOS`, `Android`, `Windows`, `macOS`, `ChromeOS`, `Linux`)
     - `osVersion` (e.g. `17.2`, `14`, `11`)
     - `browser` (e.g. `Chrome`, `Safari`, `Edge`, `Firefox`, `Samsung Internet`, `Opera`)
     - `browserVersion`
     - `model` (phone/tablet model when the browser exposes it, e.g. `Pixel 7`)
     - `ipAddress`
     - `language` (e.g. `en-US`)
     - `timezone` (e.g. `Asia/Karachi`)
     - `screen` (e.g. `390x844@3x`)
     - `userAgent`
     - `capturedAt`: `Date` (default: now)
   - `timestamps: true`

2. **Question Model (`src/models/Question.ts`):**
   - `title`: `String` (required, trimmed)
   - `options`: Array of `{ key: string, emoji: string, label: string, count: number }` (minimum 2 options)
   - `voterRecords`: Array of `{ studentId: string, fullName: string, optionKey: string, votedAt: Date }`
   - `isActive`: `Boolean` (default: `true`)
   - `createdBy`: `String` (default: `"Admin"`)
   - `timestamps: true`

### Signup Device Capture (`src/device.ts`)

Export `buildSignupDevice(req: Request, client: unknown): SignupDevice`, used only by the signup route. The device name and OS user name are NOT readable by any web page (browsers withhold them on purpose), so never ask the user for them and never store an OS user name. Instead:

- **From the HTTP request (authoritative):** parse the `User-Agent` header (hand-written regex parser, no extra dependency) into `os`, `osVersion`, `browser`, `browserVersion`, `model` (Android only, ignoring Chrome's reduced-UA placeholder `K`), and `deviceType` (`tablet` for iPad / Android without `Mobile`; `mobile` for iPhone / `Mobi`; otherwise `desktop`). Take `ipAddress` from `req.ip`, stripping any `::ffff:` prefix.
- **From the optional `device` object in the request body (untrusted):** accept only `language`, `timezone`, `screen`, `maxTouchPoints`, and `clientHints: { platform, platformVersion, model }`. Strip control characters, trim, and length-limit every string. Ignore any other keys, including any client-supplied device name.
- **Client Hints override the frozen User-Agent:** if `clientHints.platform` is present use it as `os` (`"Chrome OS"` → `ChromeOS`); if `platformVersion` is present use it as `osVersion`, except on Windows where a major version `>= 13` means `11` and anything lower means `10`. Use `clientHints.model` as `model` when present.
- **iPadOS detection:** if the resolved `os` is `macOS` and `maxTouchPoints > 1`, set `os = "iPadOS"`, `deviceType = "tablet"`, and `osVersion = ""` (the UA only exposes a frozen macOS version, so do not store a wrong one).
- **Generated `deviceName`:** `"<model> (<os> <osVersion>)"` when a real model is known (not the bare `iPhone` / `iPad`), otherwise `"<os> <osVersion> <deviceType>"` (e.g. `Pixel 7 (Android 14)`, `Windows 11 desktop`).
- Missing or malformed `device` input must never fail signup: fall back to User-Agent-only data.

### REST API Endpoints & Auth Rules

Use Bearer JWT tokens (`Authorization: Bearer <token>`):

1. `POST /api/auth/signup`:
   - Requires `fullName`, `email`, `studentId`, and `password`. Accepts an optional `device` object (see "Signup Device Capture").
   - Always assigns `role: "student"` (never allow role selection from signup request).
   - Builds `signupDevice` with `buildSignupDevice(req, req.body.device)` and stores it on the new user document.
   - Hashes `password` with `bcryptjs` (`10` rounds) and returns `{ token, user }`.
   - `user` contains only `id`, `fullName`, `email`, `studentId`, `role`. `signupDevice` is stored in MongoDB but is NEVER included in any API response.
2. `POST /api/auth/login`:
   - Requires `email` and `password`.
   - Verifies `password` strictly against `user.passwordHash` in MongoDB using `bcrypt.compare()`.
   - Returns `{ token, user }` where `user.role` comes from MongoDB (if a user's role is updated to `"admin"` in the database, logging in routes them to the Admin screen).
3. `GET /api/auth/me`:
   - Authenticated route. Looks up the user by ID in MongoDB and returns `{ user }` with their current database role.
4. `GET /api/questions`:
   - Authenticated route. Returns `{ questions }` sorted by `createdAt: -1`.
5. `POST /api/questions`:
   - Authenticated + `requireAdmin` middleware.
   - Accepts `{ title, options: [{ emoji, label }] }`, generates snake_case `key`s, sets `count: 0`, and creates the question.
6. `PATCH /api/questions/:id/vote`:
   - Authenticated route. Accepts `{ optionKey }`.
   - Checks `question.voterRecords` for `req.user.studentId` (case-insensitive):
     - If the student has not voted on this question yet: increments `targetOption.count += 1` and pushes `{ studentId, fullName, optionKey, votedAt }`.
     - If the student already voted for a different option on this question: decrements the previous option's `count` by 1, increments the new `targetOption.count += 1`, and updates their `voterRecords` entry.
     - If clicking the same option again: returns current question unchanged.
   - Saves and returns `{ question }` immediately (stateless HTTP).
7. `DELETE /api/questions/:id`:
   - Authenticated + `requireAdmin` middleware. Deletes the question by ID.

  - Export `collectDevicePayload(): Promise<DevicePayload>` where `DevicePayload = { language, timezone, screen, maxTouchPoints, clientHints: { platform?, platformVersion?, model? } }`.
  - `language` = `navigator.language`; `timezone` = `Intl.DateTimeFormat().resolvedOptions().timeZone`; `screen` = `` `${screen.width}x${screen.height}@${devicePixelRatio}x` ``; `maxTouchPoints` = `navigator.maxTouchPoints`.
  - `clientHints` come from `navigator.userAgentData` (`platform`, plus `getHighEntropyValues(["platformVersion", "model"])`) inside a try/catch; on browsers without it (Safari, Firefox) leave it empty and let the server fall back to the User-Agent.
  - On Sign Up submit, `await collectDevicePayload()` and send the result as `device` in the `POST /api/auth/signup` body alongside `fullName`, `email`, `studentId`, and `password`. Log In sends no device data.
- **Routing after Auth (`src/App.tsx`):**
  - If `!user` -> render `<AuthScreen />`
  - If `user.role === "admin"` -> render `<AdminProjectorView />`
  - If `user.role === "student"` -> render `<StudentPollView />`

## 4. Acceptance Checks for Device Capture

After implementing, verify by signing up with several different `User-Agent` values against the real signup route and reading the stored user back from MongoDB:

- iPhone Safari → `os: "iOS"`, `deviceType: "mobile"`, `model: "iPhone"`.
- Android Chrome (`Pixel 7`) → `os: "Android"`, `model: "Pixel 7"`, `deviceName: "Pixel 7 (Android 14)"`.
- Android Chrome with reduced UA (`Android 10; K`) plus client hints `{ platform: "Android", platformVersion: "14.0.0", model: "SM-S918B" }` → `os: "Android"`, `osVersion: "14.0.0"`, `model: "SM-S918B"`.
- Windows Edge with client hint `platformVersion: "15.0.0"` → `os: "Windows"`, `osVersion: "11"`, `browser: "Edge"`.
- macOS Chrome with `platformVersion: "14.2.1"` → `os: "macOS"`, `osVersion: "14.2.1"`.
- Safari on a Mac UA with `maxTouchPoints: 5` → `os: "iPadOS"`, `deviceType: "tablet"`, `osVersion: ""`.
- Garbage `User-Agent` and a non-object `device` body → signup still succeeds (`201`) with `os: "Unknown"`.
- A request with header `X-Forwarded-For: 203.0.113.7` through `127.0.0.1` → stored `ipAddress` is `203.0.113.7`.
- No API response (signup, login, `/auth/me`) ever contains `signupDevice`.
